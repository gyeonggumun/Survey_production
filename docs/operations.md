# 운영 점검 및 복구 절차

## 현재 상태와 범위

- 앱: `https://survey-production.vercel.app` / Vercel 프로젝트 `survey-production` / GitHub `main` 푸시로 자동 배포.
- DB: Supabase 프로젝트 `blhxyoloslthrdpiwfks` (`survey-maker`). 데이터베이스 변경은 `supabase/migrations/`를 기준으로 **별도 적용**하며 Vercel 배포만으로 반영되지 않습니다.
- Supabase Free 플랜의 프로젝트 백업은 자동 복구 수단으로 간주하지 않습니다. 백업 상태를 대시보드에서 확인하고, 공개 운영 중에는 변경 전·정기 백업과 복원 연습이 필요합니다.
- 이 저장소에는 DB 비밀번호, 서비스 역할 키, 사용자 데이터, 백업 파일을 넣지 않습니다.

## DB 변경 전 백업

1. Supabase 대시보드의 해당 프로젝트 ref를 확인합니다. 데이터베이스 접속 정보를 **로컬 환경 변수** `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`에 설정합니다. `pg_dump`와 `pg_restore`가 설치돼 있어야 합니다. 연결은 데이터베이스 직접 연결 또는 세션 풀러를 사용하고 트랜잭션 풀러는 피합니다.
2. 저장소 **밖**의 접근 제한된 암호화 저장소를 선택하고 `./scripts/backup-database.ps1 -OutputDirectory C:\secure-backups\survey-production`을 실행합니다. 이 스크립트는 앱에 필요한 `public`, `auth` 스키마를 custom-format으로 내보내고 아카이브 목록 및 SHA256을 확인합니다. 백업 파일 자체에는 사용자 이메일·응답이 들어갈 수 있습니다.
3. 백업 파일·해시·생성 시각·프로젝트 ref를 별도 안전한 운영 기록에 남깁니다. 복구 연습을 하지 않은 백업은 복구 가능하다고 주장하지 않습니다. Storage 파일을 쓰게 되면 별도 오브젝트 백업 절차도 추가합니다.

## 배포·마이그레이션 순서

1. PR에서 `npm run build`와 관련 테스트 결과를 확인합니다. 새 DB migration은 대상 프로젝트와 SQL, 데이터 영향, 백업을 먼저 점검합니다.
2. `supabase db push --dry-run`으로 적용 목록을 확인한 다음, 필요할 때 실제 마이그레이션을 적용합니다. 앱과 DB가 함께 바뀌면 구버전·신버전 앱 모두에서 작동하는 순서로 나누어 배포합니다.
3. `main` 푸시 후 Vercel 배포가 `Ready`인지 확인하고, 로그인→설문 생성·발행→비로그인 응답→소유자 결과 확인을 테스트합니다. 실제 운영 응답을 테스트에 사용하거나 삭제하지 않습니다.

## 장애 대응

1. Vercel Deployments·Functions 로그와 Supabase 프로젝트 상태·Database/Auth 로그를 확인하고 발생 시각 및 영향을 기록합니다. 프런트만 문제라면 직전 정상 Vercel 배포로 롤백할 수 있으나 DB 변경은 자동 롤백되지 않습니다.
2. DB 손상 의심 시 쓰기 작업을 중지하고, 마지막 백업과 이후 변경량을 파악합니다. **운영 DB에 곧바로 복원하지 말고** 별도 테스트 프로젝트에서 아카이브를 복원해 스키마·회원·설문·응답을 검사합니다.
3. 복원 검증 후 사용자 영향과 데이터 손실 가능성을 평가하여 운영 복구를 결정합니다. 원인과 재발 방지 조치를 운영 기록에 남깁니다.

## 주기 점검

- 매일: 배포 주소 접근, Vercel 최근 배포 상태, Supabase 프로젝트 상태와 인증/DB 오류를 확인합니다.
- 매주: 응답 수·DB 사용량·오류 증가를 살피고 외부 공개 설문 남용 여부를 확인합니다.
- DB 변경 전과 정해진 주기: 백업 생성·외부 보관 및 테스트 프로젝트 복원 연습을 합니다. 실제 백업 주기·담당자·보존기간은 운영자가 결정해야 합니다.
